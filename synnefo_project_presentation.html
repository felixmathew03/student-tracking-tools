03 / 33SYNNEFO • STUDENT OPERATIONS
Dynamic RBAC

The most important authorization design

MODEL

USER → ROLE(S) → PERMISSION(S) → SCOPE

SUPER ADMIN

Can create, edit, deactivate and assign roles and permissions at any time.

PERMISSION

Granular capability such as student.create, batch.assign, attendance.mark or fees.edit.

SCOPE

Optional self / assigned students or batches / domain / all.

NO HARD-CODED ROLES

Application logic checks capabilities, not fixed role names.

AUDIT

All RBAC changes are auditable.

16 / 33SYNNEFO • STUDENT OPERATIONS
Git Workflow

Three developers working safely

TEAM

Three developers work in parallel with shared standards, shared repository and clear feature ownership.

BRANCHES

main = production-ready; develop/integration = shared; feature/* = focused work.

OWNERSHIP

Split work by domain/features, but keep architecture and coding standards shared across all three developers.

COMMITS

feat:, fix:, refactor:, docs:, test:, chore:.

PR REVIEW

Every developer reviews another developer's PR; avoid self-merging and keep PRs small.

PROTECTION

No direct main pushes; CI checks required before merge.

SYNC

Pull/rebase before work; communicate overlapping changes and resolve conflicts early.

SECRETS

Never commit credentials, tokens, DB passwords or production configuration.

Important Things Not To Forget

Additional project safeguards

HISTORICAL SAFETY

Do not silently overwrite records when batches/programs change.

CONCURRENCY

Protect payments, transfers and permission changes from conflicting updates.

OBSERVABILITY

Structured logs, error tracking and health checks.

BACKUPS

Define database backup, restore and rollback procedures.

FILE STORAGE

Use restricted object storage; signed URLs for controlled file access where appropriate.

DATA RETENTION

Define retention/access rules for sensitive records and uploaded documents.

ERROR HANDLING

Use consistent API errors and user-friendly UI messages.

Final Principles

How to keep Synnefo maintainable

01

Student is the long-lived entity.

02

Historical records survive operational changes.

03

Super Admin controls roles and permissions dynamically.

04

Authorization is capability + scope based, not role-name based.

05

Backend authorization is authoritative.

06

Every important mutation is auditable.

07

Configuration replaces hard-coded business values.

08

Documentation, tests and workflows ship with features.
