Synnefo Student Operations Platform: MongoDB Schema

45 collections, 3NF-style normalized. Every document also has _id, created_at, updated_at. Field flags: ? optional, ! unique. Click a node to highlight its relations and jump to its table.

Relationship map

Design rules applied

  • Derived values are never stored: final payable, paid/balance/overdue, attendance %, exam percentage/grade, late submission, current batch (the open batch_enrollments row), a session's program, student email (lives in users).
  • History as relationships: batch transfer closes one batch_enrollments row and opens another. Attendance points to sessions + students only, so transfers and cross-batch attendance never rewrite it.
  • Shared batches: batch_programs lets one batch (e.g. Frontend) serve Python Full Stack and MERN. curriculum_items are separate documents per program unless deliberately linked to several programs via program_curriculum.
  • Assignments = projects: one assignments collection with a kind field; internship tasks are assignments with internship_id.
  • Embedding only for atomic owned parts (address, file metadata, interview criterion scores). Sensitive domains (discipline, grievances) are separate collections for restricted access.
  • Files: store in private object storage (S3 / Cloudflare R2, signed URLs); MongoDB keeps only metadata (file = storage_key, name, mime, size).
  • Auditing: audit_logs is append-only, event-level, generic by design (the one intentional polymorphic reference). T&C is static, so only students.tc_accepted_at is kept. Program transfer is supported by the model but the carry-forward decision collection is left out for now.
