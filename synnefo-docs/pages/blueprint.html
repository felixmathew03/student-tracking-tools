Blueprint explained: sprints, data distribution and UI structure

A detailed walk-through of how the project is delivered. Every sprint is explained with its reasoning, how data moves, the collections it creates, the screens it ships, business rules, tests and open decisions. Tables are generated from a copy of the data used on the Schema, UI Structure and Sprint Plan pages, so they agree with them as of today. If you change those pages, update the matching data block here too.

1. How the plan is ordered

Dependencies first

Sprints follow the references in the schema. Login and permissions come first, then master data, then people placed into batches, then everything that points at a student or a session.

Vertical slices

Each sprint ships schema, API, screens and a demo together, so you can open the running app at the end of every sprint instead of waiting for a big finish.

Risky rules early

Batch history and attendance (S2, S3) come before comfort features, because the whole product depends on them being right. Money (S5) comes before notifications that depend on it.

Student portal alongside

Student screens ship in the same sprint as the staff screens they mirror (My Attendance with Attendance, My Fees with Fees), so every module is checked from both sides.

2.3 How data is shared between modules

Reference, do not copy

A record stores the id of what it belongs to (student_id, session_id, installment_id) and never a copy of its name or batch. Changing a name or transferring a batch updates one place.

Compute, do not store

Attendance %, fee balance, installment status, grade, late submissions, current batch and a session's program are calculated when read. They cannot drift out of sync.

History by rows, not by overwriting

Batch changes close one row and open another. Payments and audit entries are never edited. Corrections are new records with a reason.

Embed only small owned parts

Address, file metadata (key, name, type, size) and interview criterion scores live inside their parent because they have no life of their own. Everything else is its own collection.

Restricted data stays separate

Conduct records and grievances have their own collections and permission keys, so access can be limited without touching the student record.

Files live outside the database

Documents go to private object storage (S3 or Cloudflare R2). MongoDB keeps only the metadata and a storage key; downloads use short-lived signed links.

4. UI structure

4.1 Layout and patterns

App shell

Role-based sidebar (only screens the role may open), top bar with global student search, notification bell and profile menu. Staff screens are desktop-first; the student portal (/me/...) is mobile-first.

List page

Search, filters, table, pagination and a Create button. Create and edit open in a modal or drawer, so there are few separate form pages.

Detail page with tabs

Used where one record has many related parts: Student 360, Batch Detail, Drive Pipeline. Tabs load their data only when opened.

Wizard

The Admission Wizard walks through identity, program, batch, fee plan and documents, then saves everything in one transaction.

Reason dialog

Required for attendance corrections, result changes, batch transfers and payment corrections. The reason is saved with the change in the audit log.

Route guard

Every route checks a permission key. Restricted screens (conduct, grievances) are hidden from other roles and also refused by the API.
