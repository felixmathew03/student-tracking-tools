Claude Code toolkit for the Synnefo MERN project

Which skills, plugins, MCP servers and hooks to set up, and where each one helps across the development lifecycle. Plugin and server names change over time, so run /plugin inside Claude Code to browse what is currently available and read each tool's own README before installing.

The building blocks

CLAUDE.md

Always-on project memory that Claude reads every session: stack, commands, coding rules. Keep it short (under about 200 lines). Generate a first draft with /init.

always loadedteam-shared via git

Skills

Reusable instructions Claude loads when relevant, or when you type /skill-name. Each is a folder with a SKILL.md. Best for repeatable workflows such as "create an API module".

.claude/skills/<name>/SKILL.md

Subagents

Specialist helpers that work in their own isolated context and report back (reviewer, test writer, debugger). Keeps the main conversation clean.

.claude/agents/

Hooks

Commands that run automatically at lifecycle events (after an edit, before a tool runs). Claude cannot forget or skip them, so use them for formatting, linting and guardrails.

settings.json

MCP servers

Connections to outside systems: GitHub, a database, a browser, error tracking. They give Claude tools it does not have by default.

.mcp.jsonclaude mcp add

Plugins

The packaging layer. One plugin can bundle skills, subagents, hooks and MCP servers. Install with /plugin install name@marketplace; plugin skills are namespaced like /plugin-name:skill.

/plugin
Rule of thumb: CLAUDE.md = what is always true. Skill = how to do a task. Hook = must always happen. MCP = reach an outside system. Subagent = isolated specialist. Plugin = share it all as one install.

Lifecycle map

Each stage lists what to use. "Write your own" means a skill or file you create once for Synnefo (examples further down); everything else is installed.

Starter files

CLAUDE.md (project root)

# Synnefo Student Operations Platform
MERN: React (Vite) + Express + MongoDB (Mongoose). Docs: @docs/schema.md @docs/ui-structure.md

## Commands
- Server: `npm run dev -w server`, tests `npm test -w server`
- Client: `npm run dev -w client`, tests `npm test -w client`
- Lint/format: `npm run lint`, `npm run format`

## Architecture rules
- One folder per domain: server/src/modules/<domain>/{model,routes,controller,service}
- Never store derived values (fee balance, attendance %, grade); compute on read.
- Attendance links to session_id + student_id only; batch history lives in batch_enrollments.
- Money uses Decimal128. Payments are immutable; corrections are new records.
- Sensitive changes (batch transfer, attendance correction, results, fees) write to audit_logs with a reason.
- Every route checks a permission key; conduct and grievance routes are restricted.

## Style
- Zod validates every request body. No business logic in controllers.
- Conventional commits (feat:, fix:, docs:). PRs need tests.

.mcp.json (shared with the team via git)

{
  "mcpServers": {
    "github":     { "type": "http", "url": "https://api.githubcopilot.com/mcp/" },
    "playwright": { "command": "npx", "args": ["-y", "@playwright/mcp@latest"] },
    "mongodb":    { "command": "npx", "args": ["-y", "mongodb-mcp-server", "--readOnly"],
                    "env": { "MDB_MCP_CONNECTION_STRING": "${MONGODB_DEV_URI}" } }
  }
}

Add servers from the terminal with claude mcp add --transport http github https://api.githubcopilot.com/mcp/ --scope project, then check with claude mcp list. Project-scoped servers ask each person to approve them first. Confirm the MongoDB server's exact flag and variable names in its README.

.claude/skills/api-module/SKILL.md (write your own)

---
name: api-module
description: Create or change an Express API module (Mongoose model, Zod schema, service, controller, routes, tests) following Synnefo conventions. Use when adding backend features.
---
1. Read the collection in docs/schema.md: fields, indexes, unique rules.
2. Create the model with the exact indexes. Do not store derived values.
3. Add Zod schemas, service (business rules), thin controller, routes with permission middleware.
4. For sensitive changes call the audit logger with a reason.
5. Write Supertest tests for the main rule and one permission failure. Run them.

.claude/settings.json (hooks and guardrails)

{
  "permissions": { "deny": ["Read(./.env)", "Read(./.env.*)"] },
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{ "type": "command",
                  "command": "jq -r '.tool_input.file_path' | xargs -r npx prettier --write" }]
    }]
  }
}

Hooks receive event details as JSON on standard input. Check the hooks documentation for the exact fields in your version.

Suggested rollout

  1. Day 1: run /init, trim the generated CLAUDE.md to the rules above, add the settings and prettier hook, commit them.
  2. Sprint 0: install the GitHub MCP/plugin, commit-commands, security-guidance; write the api-module, mongoose-model and react-feature skills.
  3. Sprint 1 to 3: add feature-dev for each module, Playwright MCP for UI checks, read-only MongoDB MCP on the dev database.
  4. Before the pilot (S6): add code-review or pr-review-toolkit to every PR, Sentry MCP, and the release skill.
  5. Ongoing: when Claude gets something wrong twice, turn it into a CLAUDE.md rule, a skill or a hook.

Safety notes

  • Trust what you install. Plugins, skills and MCP servers can run code and reach your data. Prefer the official marketplace and well-known servers, and read what a third-party one does first.
  • Keep secrets out. Store keys in environment variables (${VAR} in .mcp.json), deny reading .env files, never commit tokens.
  • Database access is read-only and development-only. This system holds fees, grievances and conduct records. Never point an MCP server at production.
  • Review before merging. Claude's output is a draft for human review; tests and CI stay the gate.
